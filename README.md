# StarliDigital

Open-source extraction of the new StarliDigital product: one company per self-hosted installation, bots, teams, Boss coordination, conversations between agents, and generated app previews. Sales pages are excluded. This is an integration workspace, not a completed release.

The frontend lives in `product/`, with its native runtime in `product-backend/`. Its exact source and verification limits are recorded in [new product source](docs/new-product-source.md). The superseded frontend has been removed from the current tree. `dashboard/backend` retains the native foundation libraries and their upstream notices; the new installer serves only `product/`.

## Getting started

The native installer now builds `product/` and runs its native company backend. With Node 24, Python 3.11 and `uv` installed, use these commands from the checkout:

```sh
npm run install:app
npm start
```

Open the printed loopback URL. A fresh installation asks you to create its administrator account and sole company once. Later visits open the workspace or sign-in; public registration and company creation/switching are unavailable. Create your bots and connect your own OpenRouter key through `/api/local/provider` or the team model-connection panel. The selected model is Nemotron Ultra free; the application disables paid model fallback. A configured key is not evidence of a successful model reply.

The new frontend runs locally. Historical fresh-checkout installation, owner login, company/two-bot/team creation and real process-restart persistence passed on Windows, macOS and Linux at code commit `8283115`. See the [three-OS installation run](https://github.com/chas7sb/starlidigital/actions/runs/45015272789). Validation of the subsequent single-company, browser-first setup is in progress.

Real OpenRouter Nemotron Ultra replies were verified in the local Windows app: Boss requested work from Pico and Pixel, Pixel used values newly generated by Pico, and Boss synthesized both replies. The passing handoff used five actual model calls at zero reported cost, and persisted after browser reload. Each new installation still needs its own explicit provider connection. See [verification scope](docs/new-product-validation.md).

Generated-app workers, their trusted previews and autonomous tool execution remain unconfigured. These checks do not establish full feature parity. See [installation](docs/install.md), [API coverage](docs/new-product-api-coverage.md) and [backend contract](product-backend/runtime-contract.json).

The native server runs in the foreground; stop it with Ctrl+C. Keep the extracted project in a writable, persistent directory. Node 24+, `uv`, and FFmpeg are prerequisites; the installer prepares the separate application runtimes. QEMU is an additional prerequisite for the isolated computer.

Windows, macOS and Linux are installation targets. Platform validation and outstanding requirements are recorded in the installation and [VM runtime](docs/runtime.md) guides. A running application container does not establish that a computer-use VM is ready.

## Source layout

| Directory | Contents |
| --- | --- |
| `product/` | New StarliDigital bots, teams and Boss frontend |
| `product-backend/` | Native company, orchestration and app runtime source |
| `dashboard/` | Retained native backend foundation, metadata and upstream notices |
| `platform/` | Node platform, active MCP control-plane, CLI and device source |
| `platform/extensions/` | Additional production feature runtimes, extracted without live state |
| `runtime/` | Isolated computer-use VM lifecycle |
| `installer/` | Local deployment and setup entry points |
| `config/` | Fresh-instance configuration examples |
| `security/` | Provenance and privacy review tooling |
| `qa/` | Source contracts and runtime acceptance checks |
| `packaging/` | Reproducible source archive and CI tooling |
