# New product: bots, teams and execution integration review

Read-only source review on 2026-11-22. The UI target is `product/` V12, as identified in `new-product-source.md`. The old dashboard frontend is not a substitute. Some canonical Python backend libraries currently remain under `dashboard/backend`; using those libraries does not imply serving the old UI.

For paths below, **W** means `product-backend/server-src/grokbot-gemini-autonomous-company-wave1-20261120`; **A** means `W/codex/assembly-r1`. `product-backend/candidate-source/` is an additional inspection snapshot. Preserve the mirrored `server-src/` hierarchy when resolving the relative Node imports.

**Conclusion.** The source contains genuine company message dispatch and a separate bounded model-driven app-building workflow. It does not establish general autonomous bot-to-bot conversation in the active company-chat adapter. The newly added `product-backend/local_server.py` currently provides native auth/company/messaging/guest-claim foundations while explicitly reporting provider and worker execution as unconfigured. That is an honest foundation, not completion of the requested autonomous product.

**Company chat dispatch, including the important human-source fence.** The native company messaging mount reads the actual session and company authority, and invokes `app.state.company_messaging_start_turn` only through the installed runtime ingress. The relevant canonical libraries are `dashboard/backend/company_messaging/{native_mount,http,store,native_capabilities}.py` and `dashboard/backend/starli_company_computer/runtime/company_bot_runtime/{core,router}.py`.

`Runtime.start_from_message()` in `company_bot_runtime/core.py` requires the source speaker to equal the authenticated human, rejects deleted messages, and requires an explicit agent mention. `Runtime.start()` checks that source again before creating a turn, validates current actor/room/provider scope, prevents overlapping active turns for the same room/bot, saves human/assistant message IDs, then schedules `_run()`. It explicitly rejects `work_session` rooms with `SUPERVISED_SESSION_RUNTIME_REQUIRED`.

The active staged override is `A/adapters/native_company_chat_with_transfer.py`: `install_native_chat()` binds `NativeChat.start_turn` and authorization callbacks; `NativeChat._run()` freshly fences authority, adds verified imported history and existing-app facts, makes one `provider.complete()` call, persists a provider receipt, and marks the turn `ANSWERED`. Its instruction explicitly says this turn has no new execution tools and must not claim new building, edits, messages or browsing. It does not feed the assistant result back into message dispatch. The simpler `native_company_chat.py` is also conversation-only and lacks the history/facts enrichment.

Consequently, multiple bots replying to one human message are genuine model fan-out if that adapter/provider is installed. They are not a demonstrated autonomous A→B→A conversation. General agent-to-agent execution needs a separately scoped agent-authored ingress, authority/budget/cancellation fences and real receipts; it must not be implemented by deleting the human-source check or inventing messages/receipts.

**The genuine bounded autonomous workflow is separate.** The richest recovered composition is `A/scripts/start_native_model_apps.py`, which installs more than `start_native_chat.py`: guest company authority, imported-history resolution, model-build gateway/lifecycle, verified owner facts, claim guards and controlled reopen support.

The model-driven path is:

1. `codex/guest-build-tools-r1/guest_build_tools.py` exposes exactly `build_app` to `GuestToolProvider`. A real model tool call is validated and bound to the canonical guest message/conversation hash and server-owned authority context.
2. `codex/model-app-execution-r1/guest_model_build.py` admits a durable, idempotent build; revalidates company/project/room/principal and conversation prefix; creates exactly BACKEND and FRONTEND worker bindings; and starts a bounded task.
3. `model_node_dispatcher.py` invokes the Node CLI through private stdin/stdout and responds to repeated authority checks. `native-worker-service.ts` composes the canonical capability, agency-execution, machinery and orchestration services with durable graph/receipt adapters.
4. `model-native-worker.py` makes one real model call per worker. BACKEND produces declarative app/routes schemas, not executable server code. FRONTEND receives the verified backend artifact/agency receipt as an explicit dependency, then generates React/API source. The service checks worker identity, scope, model-call count and provider receipt before accepting output.
5. `model-app-persistence-r2/model_app_lifecycle.py` and the compiler/runtime adapters validate, compile, launch and persist the resulting application under separate lease/generation/storage authority. Readiness requires their actual receipts, not a chat response.

This is real bounded worker collaboration via a verified artifact dependency. It is distinct from free-form peer-agent chat.

The explicit post-claim `Start building` path in `codex/native-wiring-r3/native_claim_execution_routes.py` is another class: it registers two `DETERMINISTIC_LOCAL` workers, and its `native-worker-service.ts` validates `modelCalls:0`. Do not present this branch as model-generated autonomous development. The model-app-execution branch validates `OPENROUTER_MODEL` and actual provider receipts instead.

**Current portable composition and closure gaps.** These are integration findings, not recommendations to copy production state.

- `product-backend/local_server.py` is a new local composition, not the original upstream staging script. It deliberately redirects native imports to repository backend libraries, uses fresh protected state under `work/`, mounts selected native auth/company/directory/messaging/guest/claim surfaces, disables public signup, and creates the first owner interactively. Its `/health` currently says `providerConfigured:false`, `modelExecution:NOT_CONFIGURED`, and `workerExecution:NOT_CONFIGURED`; orchestration requests return503. No native chat runtime, OpenRouter provider or model app lifecycle is installed there yet. Do not interpret its successful foundation tests as bot replies or autonomous execution.
- The product UI needs route coverage beyond that composition. In particular, personal `/api/v1/starli/group-chats` and company bot profile/provider-selection/provider-options/memory routes are not established by the selected mounts. The settings client may fall back to a read-only directory profile, but that does not implement saves, model configuration or memory. An explicit route-to-service/migration matrix is required before claiming all bots/teams/settings features work.
- The original native harness and chat adapters refer to `/srv/starlidigital/webui-releases/native-company-mcp-always-v33-20261119/backend`. Canonical auth/models/config, company authority, company messaging, bot runtime, memory/directory modules and their transitive dependencies must remain in the package closure or be mapped to reviewed local counterparts. The current local server intentionally reuses `dashboard/backend`; `product-backend/` alone is not yet standalone.
- Preserve the `server-src/` Node layout. For example, `codex/native-wiring-r3/native-worker-cli.ts` imports `../../../store.ts`. From the mirrored W location this reaches `product-backend/server-src/store.ts`, which exists. From the flattened `candidate-source/codex` copy it reaches `product-backend/store.ts`, which does not. Do not launch the flattened inspection copy unchanged.
- `SOURCE-MANIFEST.json` records unresolved source references. Some `.js` imports can legitimately resolve to `.ts` under tsx; distinguish those from absent source. Actual missing/relocated historical baseline files, native-source frontend templates, Node dependency locks and dynamic import paths still need a verified import/build/launch closure. Source hashes alone do not execute that graph.
- The joined supervisor depends on a generated service/route configuration, fresh per-service nonces and private control state. Original private supervisor/demo configuration must not be copied. Regenerate the logical topology against local sources and fresh state; preserve streaming/cancellation and identity semantics.
