## Integration points

`StarliAutomations.svelte` is the single management panel for Starli Automations, Starli Integrations, canonical approvals and execution history. Props: `companyId`, `actorId`, `conversationId` (optional empty), `accessSignal`. Events: `close`, `denied {status}`, `changed {companyId,conversationId}`, `openConversation {conversationId}`. The parent owns actual room navigation. Pass the exact canonical room ID; an empty room permits browsing company resources but blocks setup/connection creation.

Reusable conversation cards use the same DTOs and CSS:

- `AutomationSetupCard`: `draft`, `connectors`, `busy`, `authorization`. Events `answer` (one configuration patch), `connect {providerId}`, `refresh`. It displays only `draft.missing[0]`. Each answer must call `client.answer(draft, patch)` and use the returned persisted revision; do not append field answers/passwords to a model prompt or local storage. The connection card lists requested scopes. The dedicated provider authorization link is only shown after a verified authorization receipt. An unavailable provider setup is explicitly unavailable, never connected.
- `AutomationReviewCard`: `draft` or `workflow`, `test`, `busy`, `engineAvailable`. Events `test`, `activate`, `pause`, `edit`, `history`, each carrying the exact resource. Server action flags gate controls. Activation additionally requires a matching successful non-destructive test receipt and explicit activation confirmation. The summary lists trigger and readable actions; it does not show technical engine internals.
- `AutomationApprovalCard`: `approval`, `actorId`, `busy`. Event `decision {approval,decision}`. It shows exact store/order/amount/currency/payment provider, assignee, expiry, workflow version and execution. The server's canDecide flag plus exact assignee and expiry gate UI; backend authority remains mandatory. Each choice has a second explicit confirmation. Workflow activation and per-action decisions remain separate.

`automations-client.ts` implements the negotiated catalog, connections/authorize, canonical room drafts, CAS updates, test, activate, pause, workflow history, canonical approvals/decision. It validates native company scope and late session/access boundaries. No engine URL, administrative credential or provider secret is accepted by any component. OAuth authorization state is ephemeral and cleared on refresh/access changes; the workflow itself remains backend persisted.

## V3 company connections and safe Slack review

`AutomationChatConnection.svelte` is the direct-chat connection host; props are `companyId`, `actorId`, the existing canonical `conversationId`, `providerId: 'slack' | 'shopify'`, and `accessSignal` (optional requestedScopes). It uses the same `AutomationConnectionCard.svelte` as workflow setup and management. Native GET `/connections/setup` supplies setup status and permission; native `/connections` supplies saved company account metadata. Shopify asks for the exact bare lowercase `*.myshopify.com` store only when the server's missing fields require it. Saving calls native authorize with `shopDomain` and the server setup revision. Even when the store is saved, unavailable private app registration remains explicitly unavailable. No client-secret/token/password input exists.

The canonical native `kind: 'connection'` card is accepted by `automationSelection` only with exact company/room/message/requesting-bot/source bindings and an allowlisted provider. Root owns its inline/menu wiring. Connecting an account does not manufacture a workflow or conversation; existing verified company grants are reused.

The production callback now supersedes all earlier raw-code UI descriptions above: a provider redirects to the backend's configured public HTTPS `/api/v1/starli/automations/oauth/{provider}/return`. The backend verifies and stores the temporary provider return and redirects to the explicitly allowed frontend `/app/integrations/{provider}/callback#handoff=OPAQUE`. The fragment is never sent to frontend HTTP logs. The frontend accepts only this fragment, removes fragment/query with history.replaceState before any exchange, and POSTs `{handoff}` with the existing native session to the shared `/api/v1/starli/automations/oauth/{provider}/complete`. It has no raw provider code/state query fallback. Verified company/room/draft IDs then navigate to the root-owned authorized resume hook; no OAuth values are stored. Root reports its signed native room-resume check passed. Actual Slack/Shopify consent still requires private platform registrations and the human's provider authorization; fixtures do not establish those accounts.

The additive `shopify_order_slack_review` intent and `slack_message_send` approval are separately typed from refunds/internal tests. The client rejects altered returned content or a refund decision for this action. Receipt rendering labels verified Slack operations correctly.
