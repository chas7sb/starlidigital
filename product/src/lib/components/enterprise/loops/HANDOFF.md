# Scheduled Loops UI — native company port

`ScheduledLoops.svelte` is one native management screen, with props `companyId`, `actorId`, `accessSignal`, and optional stable `api: ScheduledLoopsPort`. Events: `close`, `denied {status}`, `openConversation {conversationId}`, `changed {companyId,loopId}`. Root owns navigation and the actual company adapter.

The backend owner agreed to the typed-port approach while inspecting real social-loop storage and routes. The required interface is exported in `scheduled-loops.ts`; there is intentionally no guessed HTTP implementation, no account-global social fallback, no scheduler implementation and no human create method. Without a bound native company port the screen explicitly displays unavailable and starts no work.

Each loop is verified against protocol version/company/id/revision/owner bot/source chat. Native adapters must derive company membership and execution rights from the existing verified session. Destination/media choices must be freshly authorized. The UI never accepts arbitrary provider credentials or media URLs. All mutations carry expectedRevision. Publishing activation additionally carries the exact reviewed rules digest and explicit authorizePublishing:true; changes must return a new revision and immutable owner/source bindings. Adapters must invalidate publishing authorization when relevant saved rules change.

Humans can inspect text, image/video references, destinations, schedule expression, IANA timezone, next due, source chat and owner bot. They can edit, pause/resume, review ongoing publishing rules, inspect runs and delete only when corresponding server flags permit. Unsaved drafts survive remote revision conflicts; saving is disabled until the user discards the stale draft and reloads. Delete and resume have explicit confirmation; ongoing publishing activation requires an explicit checkbox and confirmation. No manual run/retry or Create control exists. Uncertain external results are shown without replay.

Controlled checks: `scheduled-loops.test.cjs` passes exact CAS/rules digest, source/company/session/abort fencing, no false pause, no create method and strict TypeScript. `verify-browser.cjs` passes eight journeys on the actual component against an injected controlled port, including dirty conflict retention, explicit ongoing-rule authorization, uncertain history,390px, delete confirmation and access clearing. Zero HTTP/provider writes; this does not establish a bound production social scheduler. `browser-receipt.json` records that distinction.

Initial native social scheduling is deliberately limited to daily HH:mm in Europe/Bucharest. The snapshot must advertise scheduleCapabilities:{kind:'daily',timezone:'Europe/Bucharest'} and return canonical HH:mm; the controller rejects other schedule/TZ shapes. The editor uses a time input and fixed visible timezone, not arbitrary cron syntax. The native adapter must not silently coerce unsupported legacy schedules into this cadence.
